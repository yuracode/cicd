##  目標

- 1人でも「3人チームの1週間」を擬似体験できる
- 自分の PR に対して **時間を置いてセルフレビュー** できる
- マージ競合（コンフリクト）を自分で意図的に起こして解決できる

##  導入

### Phase 4 までの到達

個人としては CI/CD パイプラインを組める状態になった。今回は **「もし自分がチームで動かすとしたら」** を一人で疑似体験する。

### 今回のシミュレーション設定

一人で回すが、**3人チームの振る舞いを1人で順番に演じる** ことで、チーム開発の感覚を先取りする。

- リポジトリは自分の `todo-app` をそのまま使う
- 「担当A／担当B／担当C」の3ロールを **自分1人で順に演じる**
- ロールを切り替えるタイミングで **一度離席** する（トイレ・お茶・別作業）と、第三者視点が入りやすい
- 各ロールは別の feature ブランチを担当し、PR → セルフレビュー → マージ の流れを3回回す

### シミュレーションで体験すること

1. ブランチ戦略（複数ブランチの同時進行）
2. PR コメントのやりとり（自分に対して書く）
3. コンフリクト解決
4. ブランチ保護の「CI 必須」ルールの体感

> **補助オプション：** 第2の GitHub アカウント（サブ垢）を持っている人は、そちらから Collaborator として招待し、レビュー側を別アカウントでやると「自分のPRを自分で Approve できない」GitHub の制約も含めて体験できる。無理に作る必要はない。

##  本題

### 1. セルフ運用ルールを決めて書き出す

まずノートか `docs/team-rules.md` に書いておく。**後で自分が忘れるから明文化する**。

```markdown
# ひとりチーム運用ルール

- ブランチ命名：`feature/ロール名-機能名`（例：`feature/role-a-filter`）
- main は保護（コマ17で設定済み）
- PRマージ条件：CI 全パス ＋ セルフレビュー済み
- コミットメッセージ：Conventional Commits
- PR本文：変更内容／動作確認／レビュー観点の3項目は必ず書く
```

### 2. 3つの機能を割り当てる

同じ `App.jsx` を触る機能を3つ用意する。**わざとコンフリクトが起こる設計** にする（コンフリクト解消の練習になる）。

| ロール | 機能 |
|------|------|
| ロールA | **フィルタ機能**：全／未完了／完了 の切り替え |
| ロールB | **検索機能**：テキスト入力で TODO をフィルタ |
| ロールC | **件数表示**：上部に「全○件 / 完了○件」 |

### 3. ロールA：実装 → PR → セルフレビュー

```bash
git switch main
git pull origin main
git switch -c feature/role-a-filter
```

実装（軽めで良い。流れの体験が目的）：

```jsx
// App.jsx に追加
const [filter, setFilter] = useState('all')
const visibleTodos = todos.filter((t) => {
  if (filter === 'active') return !t.completed
  if (filter === 'done') return t.completed
  return true
})

// return内に追加
<div>
  <button onClick={() => setFilter('all')}>すべて</button>
  <button onClick={() => setFilter('active')}>未完了</button>
  <button onClick={() => setFilter('done')}>完了</button>
</div>
```

テストも1件足す：

```jsx
// App.test.jsx に追加
it('フィルタを「未完了」にすると完了済みは非表示', async () => {
  // ... テスト省略 ...
})
```

コミット＆ push：

```bash
git add .
git commit -m "feat: フィルタ機能を追加"
git push -u origin feature/role-a-filter
gh pr create --title "フィルタ機能追加" --body "全/未完了/完了 の切り替え。テスト追加。"
```

**ここで5分離席する**。戻ってきてから自分の PR を開き、**初めて見る他人のコードのつもり** で読む。

```bash
gh pr view --web
```

`Files changed` タブで、次のチェックリストを自分に問いかけながら読む：

- [ ] 命名（関数・変数）が説明的か
- [ ] 不要な `console.log` が残っていないか
- [ ] 関係ない変更が混ざっていないか
- [ ] 動作確認リストが PR 本文にあるか

気になる箇所には **行コメント** を付ける。書き方のコツは後述。修正が必要なら feature ブランチに追加commit → CI が緑になったらマージ。

### 4. ロールB・Cを順番に回す

ロールA をマージしたら、main を取り込んでから次のロールを開始する。

```bash
git switch main
git pull origin main
git switch -c feature/role-b-search
```

実装（検索入力）：

```jsx
// App.jsx に追加
const [keyword, setKeyword] = useState('')
const visibleTodos = todos.filter((t) => t.text.includes(keyword))

<input
  placeholder="検索..."
  value={keyword}
  onChange={(e) => setKeyword(e.target.value)}
/>
```

commit → push → PR → セルフレビュー → マージ。同じ流れでロールCも回す。

### 5. セルフレビューコメントの書き方

1人だとつい「いいや」と流しがち。**自分に対して他人のつもりで書く** のがコツ。

**コメントのマナー：**

- **「なぜ」** を書く（「ここを〜に」→「〜だと△△なのでこうしては？」）
- **質問形で** 書く（明日の自分の意図を尊重）
- **小さな提案と重大な指摘を分ける**（`nits:` を頭につけると軽微と分かる）

**例：**

```
【良い】
このfilter関数、毎回新しい配列を作っていますが、
useMemo で囲うと再レンダリング時にキャッシュが効きます。
そうしない理由があれば PR 本文に書いておくと親切です。

【悪い】
useMemo 使えば？
```

### 6. コンフリクトを意図的に起こす

3つの機能が同じ `App.jsx` を触っているので、**2本目・3本目のマージで必ずコンフリクト** が起こる設計になっている。これがこのコマの山場。

**起きた時の解決：**

```bash
git switch feature/自分のブランチ
git fetch origin
git rebase origin/main
```

`App.jsx` にコンフリクトマーカーが出る：

```jsx
<<<<<<< HEAD
  <FilterButtons />
=======
  <SearchInput />
>>>>>>> feature/role-b-search
```

**両方残したい時は両方書く：**

```jsx
<FilterButtons />
<SearchInput />
```

マーカーを削除して保存。

```bash
git add src/App.jsx
git rebase --continue
git push --force-with-lease
```

> **`--force-with-lease`** は `--force` の安全版。リモートが想定外に進んでいたら push を止めてくれるため、思いがけない上書きを防げる。

### 7. 最終マージと動作確認

3本すべてマージできたら：

```bash
git switch main
git pull origin main
npm run dev -- --host
```

**3機能すべてが動作する** かを自分で確認。Vercelプレビュー／GitHub Pages 本番URLでも確認。

**Actions タブ** でこのコマ中に走ったワークフロー本数を見る → 10〜20本のワークフローが走っているはず。

- 自分の PR を他人目線でセルフレビューできる
- コンフリクトを rebase で解決できる

### 振り返り（自分に問いかける）

- CI が赤いまま放置していないか
- PR 本文は「なぜこの変更か」を説明できているか

##  課題

### 基礎課題（必須）

1. 今回のセルフレビューで **自分に一番刺さった指摘** を1つメモする
2. セルフレビュー中に「良いな」と思った自分の書き方を1つメモ → 次回以降も意識して使う
3. 次回までに「個人制作で何を作りたいか」を **3案** 考えてくる（Phase 5 でのアプリアイデア）

### 応用課題（推奨）

4. **PR テンプレート** `.github/PULL_REQUEST_TEMPLATE.md` を作成する：

```markdown
## 変更内容
-

## 動作確認
- [ ]
- [ ]

## レビュー観点
-
```

→ 以降、PR 作成時に自動でこのテンプレが入る。**書くべきことを毎回書かせる仕組み**。

5. **Issue と PR を紐付け** してみる：
   - Issueを作成（例：「完了日時表示機能」）
   - そのIssueを close する PR の本文に `Closes #3` と書く
   - PRマージ時に Issue が自動でCloseされることを確認

→ タスク管理とコード変更の紐付けは、後からログを追う時の強力な武器。

6. **「PRマージ条件」を正式にドキュメント化** する：承認ルール、CI必須項目、コンフリクト解消の手順など。`docs/contributing.md` などに書く

> **狙い：** 暗黙のルールは忘れられる。**明文化** しておくと、時間を置いて戻ってきた自分や、将来プロジェクトを引き継ぐ人が迷わない。

### チャレンジ課題（挑戦）

7. **GitHub Projects（カンバンボード）** を1つ作り、タスクを Todo / In Progress / Done の3列で管理してみる。PRと自動連携する機能も試す

8. **「コードレビューで指摘しない方が良いこと」** を自分用に整理する：
   - ただの好み（変数名の好み、空白の位置）→ Prettier / Lint に任せる
   - 原則論の長話 → 別ドキュメントで議論
   - 別PRですべき大きな提案 → 別 Issue に切り出す

**PRレビューは「このPRをマージすべきか」の場** という原則を自分用に1行で書き残す。

9. 個人制作の **3案を家族・友人・ChatGPT など誰か（人・AI問わず）に説明** してフィードバックをもらう：「どの案が一番面白そうか／実現可能か」。次コマの企画設計に活かす
