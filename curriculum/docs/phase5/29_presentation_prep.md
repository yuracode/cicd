# コマ29｜発表準備

| 項目 | 内容 |
|------|------|
| フェーズ | Phase 5 |
| 所要時間 | 90分 |
| 前提コマ | コマ28 個人制作③：テストとCI/CDの仕上げ |
| 次コマ | コマ30 最終発表・ふりかえり |

##  目標

- 5分の発表の構成を決め、「何を作ったか」だけでなく「どう作り・どう守り・どう届けているか」を伝えるスライドを作れる
- デモの手順を決め、失敗したときの予備（録画・スクリーンショット）を用意できる
- リハーサルで時間を計り、聞いた人からのフィードバックで発表を直せる

##  導入

### 次回が最終発表

1人 **5分（発表4分 + 質疑1分）**。聞く人は、同じ授業を受けたクラスメイトと先生。

### 何を伝える発表か

この授業の発表は「アプリの紹介」だけではない。**30コマで身につけた開発の流れを、自分のアプリで説明する** のが目的。

| 観点 | 発表で見せるもの |
|------|---------------|
| 動く | 公開 URL でのデモ |
| 守られている | テストの例、カバレッジ、CI が赤くなって止めてくれた経験 |
| 自動で届く | PR → CI → マージ → 自動公開の流れ（Actions の画面、PR の画面） |
| 説明できる | 設計の理由、公開先を選んだ理由、苦労したことと解決方法 |

### よくある失敗

- 機能の説明だけで時間が終わり、テストや CI/CD の話ができない
- デモ中にネットがつながらない・エラーが出て止まる
- スライドの文字が多く、読み上げるだけになる
- 時間を計っておらず、半分しか話せない

##  本題

### 1. 発表の構成を決める

5分（発表4分）の目安。

| 順番 | 内容 | 時間 | スライド |
|------|------|------|---------|
| 1 | タイトル・自己紹介 | 10秒 | 1枚 |
| 2 | 何のアプリか（誰の・どんな困りごとを解決するか） | 30秒 | 1枚 |
| 3 | **デモ**（公開 URL で主な操作） | 60秒 | なし（ブラウザ） |
| 4 | 設計：部品とロジックの分け方 | 30秒 | 1枚 |
| 5 | **テスト**：何をどうテストしたか、数字（件数・カバレッジ） | 40秒 | 1枚 |
| 6 | **CI/CD**：PR から公開までの流れ、実際に助けられた場面 | 40秒 | 1〜2枚 |
| 7 | 苦労したこと・工夫したこと | 20秒 | 1枚 |
| 8 | まとめ・今後やりたいこと | 10秒 | 1枚 |

**スライドは7〜8枚** が目安。1枚に言いたいことは1つ。

### 2. スライドを作る

使い慣れたツールでよい（Google スライド、PowerPoint、Canva など）。

各スライドのコツ：

| スライド | 入れるもの | 例 |
|---------|-----------|-----|
| 何のアプリか | 困りごと → 解決、を1文で | 「つい休憩しすぎる」→「25分・5分を自動で切り替え」 |
| 設計 | コマ26で書いた部品の図、`lib/` に切り出した関数の名前 | `tick(timer)` が「1秒後の状態」を返す |
| テスト | テストの **コード1つ** と、`npm run test:coverage` の数字 | 「タイマーの切り替えを25分待たずにテスト」 |
| CI/CD | コマ23のパイプラインの図、Actions の画面のスクリーンショット | 「CI が赤くなって、マージ前にバグに気づけた」 |

> **文字より図と画面**。コードを見せるなら、大事な5〜10行だけを大きく。PR の画面、Actions の画面、カバレッジの表は、スクリーンショットで見せると伝わりやすい。

### 3. 「CI/CD に助けられた話」を探す

発表で一番伝わるのは、**実際に起きたこと**。自分のリポジトリの履歴から探す。

```powershell
cd ~/workspace/<自分のアプリ>
gh run list --status failure --limit 10
gh pr list --state merged --limit 20
git log --oneline -30
```

- CI が赤くなった実行を開き、**何が原因で、どう直したか** を思い出す
- プレビュー URL で見つけた見た目の問題はなかったか
- テストを先に書いたことで、仕様が決まった場面はなかったか

見つからなければ、コマ24の練習や `todo-app` で経験したことを話してもよい。

### 4. デモの手順を決める

デモは **決めた手順どおりに** 行う。その場の思いつきで操作しない。

```markdown
## デモ手順（60秒）
1. 公開 URL を開く（あらかじめタブを開いておく）
2. スタートを押す → 数字が減ることを見せる
3. 一時停止 → リセット
4. （時間がかかる操作は）DURATIONS を短くしたプレビュー URL か、録画で見せる
5. 完了回数が増えたところを見せる
```

**予備を必ず用意する**。

| 予備 | 作り方 |
|------|-------|
| 録画 | Windows の `Win + Alt + R`（Xbox Game Bar）や、`Win + Shift + S` → 録画でデモを撮っておく |
| スクリーンショット | デモの各場面を撮ってスライドの最後に入れておく |
| 手元のアプリ | 公開 URL が開けないときに備え、`npm run dev` で動く状態にしておく |

> 25分待つような操作は、デモでは見せられない。**「テストでは25分を一瞬で確かめている」と説明する材料にできる**。

### 5. 原稿を書く

スライドごとに、**話すことを箇条書き** で書く（文章を丸暗記すると、1つ忘れたときに止まってしまう）。

```markdown
## スライド5：テスト
- タイマーの「25分たったら休憩」をどう確かめるか → 本当に25分待てない
- Jest のフェイクタイマーで、時間を一瞬で進めてテストした（コードを指す）
- lib/ はカバレッジ100%、全体で ○○ %
- テストがあったおかげで、tick の書き方を変えても安心して直せた
```

### 6. リハーサルをする

1人で、**時間を計りながら** 声に出して通す。

```text
1回目：時間を計る（たぶん長すぎる）→ 削る場所を決める
2回目：削った版で通す → 4分に収まるか確かめる
3回目：デモも含めて本番どおりに通す
```

削るときは、**機能の説明を削り、テストと CI/CD の話を残す**。

##  演習

### 演習1（基本）：スライドと原稿を完成させる

本題1〜5をもとに、スライド（7〜8枚）と原稿を完成させる。

**確認方法**：スライドに「デモ」「テスト」「CI/CD」の3つが入っていて、それぞれに話すことが原稿に書いてあればOK。

### 演習2（基本）：ペアでリハーサルする

2人1組で、お互いに本番どおり発表する。聞く人は、次のシートに記入して渡す。

| 観点 | ◎ / ○ / △ | ひとこと |
|------|----------|---------|
| 何のアプリか、最初の30秒で分かった | | |
| デモでアプリが動くことが分かった | | |
| テストで何を守っているか分かった | | |
| PR から公開までの流れが分かった | | |
| 4分に収まっていた | | |
| 一番印象に残ったこと | | |
| 1つだけ直すとしたら | | |

**確認方法**：もらったフィードバックを見て、スライドか原稿を1か所以上直せればOK。

### 演習3（応用）：質問を予想して答えを用意する

質疑応答で聞かれそうな質問を5つ考え、答えを1〜2文で用意する。

<details>
<summary>よくある質問の例</summary>

- なぜ GitHub Pages と Vercel の両方に公開したのですか？（片方だけならどちらを選びますか？）
- テストを書くのに一番苦労したところはどこですか？
- カバレッジは何 % を目指しましたか？ なぜその数字ですか？
- データはどこに保存していますか？ スマホと PC で共有できますか？
- もう1コマあったら、何を追加しますか？

</details>

**確認方法**：5つの質問と答えを書き、ペアの人に1つ質問してもらって答えられればOK。

### 演習4（早く終わった人向け）：README を発表用に磨く

発表のあと、リポジトリを見に来た人が迷わないように README を見直す。

- 一番上に、公開 URL・CI のバッジ・スクリーンショットがある
- 「何ができるか」が3行以内で分かる
- 「開発」の節のコマンドをそのまま実行して、本当に動く（別のフォルダにクローンし直して試す）

**確認方法**：別のフォルダに `gh repo clone` して、README の手順だけで `npm test` と `npm run dev` まで動けばOK。

##  まとめ

### 今日できたこと

- 5分の発表の構成を決め、デモ・テスト・CI/CD を含むスライドと原稿を作った
- デモの手順と、失敗したときの予備（録画・スクリーンショット）を用意した
- リハーサルで時間を計り、フィードバックで発表を直した

### 発表の心構え

- **うまくいかなかったことも立派な発表内容**。「CI が赤くなって、こう直した」は一番伝わる話
- デモでエラーが出たら、慌てずに予備に切り替えて「本番ではこうなります」と続ければよい
- 聞く人は、同じ30コマを一緒に学んだ仲間。専門用語を使ってもよいが、**自分の言葉で** 説明する

### 次コマ予告

次回は最終発表。発表のあと、30コマをふりかえり、身についたことと次に学ぶことを整理する。

##  課題

### 基礎課題（必須）

1. スライド・原稿・デモの予備（録画かスクリーンショット）を完成させる
2. 本番どおりのリハーサルを最低2回行い、4分に収める

### 応用課題（推奨）

3. 自分の発表を録画して見返し、「えーと」が多い場所、早口になった場所を直す
4. 演習3の質問への答えを、スライドの最後に「補足資料」として入れておく（聞かれたときに見せられる）

### チャレンジ課題（挑戦）

5. 発表の中で、**その場で小さな PR を作って CI が動く様子を見せる** デモに挑戦する。CI の実行には時間がかかるので、発表の最初に PR を作っておき、最後に結果を見せるなど、時間の使い方を工夫する
6. 発表スライドを Markdown で書ける Marp などのツールで作り、スライド自体も GitHub で管理して、GitHub Pages で公開してみる
