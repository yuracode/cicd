| 項目 | 内容 |
|------|------|
| フェーズ | Phase 5 |

| 前提コマ | コマ29 発表準備 |

##  目標

- 自分のアプリと、その開発の流れ（テスト・CI/CD・デプロイ）を5分で発表できる
- 他の人の発表を聞いて、良いところと質問を具体的に伝えられる
- 30コマで身についたことを整理し、次に学ぶことを決められる

##  導入

### 今日の流れ

1. 発表の準備（最終確認）
2. 1人5分（発表4分 + 質疑1分）で発表
3. 30コマのふりかえり
4. 次に学ぶことを決める

### 発表の前の最終確認（5分）

- [ ] 公開 URL をブラウザのタブで開いてある（Pages と Vercel の両方、使うなら）
- [ ] GitHub のリポジトリ・PR・Actions の画面をタブで開いてある
- [ ] デモの予備（録画・スクリーンショット）がすぐ出せる
- [ ] 手元で `npm run dev` がすぐ動く状態にしてある
- [ ] スライドが開いてあり、文字の大きさがプロジェクタで読める

##  本題

### 1. 発表する

コマ29で決めた構成と原稿で発表する。**時間は発表4分**。

発表者のルール：

- 最初に「何のアプリか」を一言で言う
- デモは決めた手順どおりに行う。うまくいかなければ予備に切り替える
- テストと CI/CD の話を必ず入れる

### 2. 聞く人のワークシート

聞く人は、発表ごとに次を書く。発表が終わったら、書いたものを発表者に渡す（またはリポジトリの Issue にコメントする）。

| 項目 | 書くこと |
|------|---------|
| 良かったところ | 具体的に1つ（例：「テストで25分を一瞬で確かめているのが分かりやすかった」） |
| 質問 | 1つ（質疑の時間に聞けなかったら、Issue で聞く） |
| 自分のアプリに取り入れたいこと | 1つ |

> 良いところは **具体的に**。「すごかったです」より「PR の画面で CI とプレビューが並んでいるのを見て、流れがよく分かりました」のほうが、発表した人の次につながる。

### 3. 自分の発表をふりかえる

全員の発表が終わったら、自分の発表について書く。

| 観点 | ◎ / ○ / △ | 理由 |
|------|----------|------|
| 公開 URL でアプリが動くことを見せられた | | |
| テストで何を守っているかを説明できた | | |
| PR から公開までの流れを説明できた | | |
| 設計の理由を自分の言葉で話せた | | |
| 4分に収まった | | |

もらったワークシートを読み、**次に発表するときに変えたいこと** を1つ書く。

##  演習

### 演習1（基本）：もらったフィードバックを Issue にする

発表でもらった「質問」と「1つだけ直すとしたら」を、自分のアプリのリポジトリに Issue として登録する。

**確認方法**：フィードバックから Issue が1つ以上でき、ラベル（`enhancement` など）が付いていればOK。

### 演習2（基本）：ふりかえりを README に書く

自分のアプリの README の最後に「ふりかえり」の節を作り、次の3つを書く。

- 一番苦労したことと、どう解決したか
- テストや CI/CD があって助かった場面
- 次に追加したい機能

**確認方法**：PR でマージされ、公開されている README で読めればOK。

### 演習3（応用）：フィードバックを1つ直してリリースする

演習1の Issue のうち、すぐ直せるものを1つ選んで、いつもの流れ（ブランチ → PR → CI → マージ → 公開）で直し、`v1.0.1` としてリリースする。

**確認方法**：Releases に v1.0.1 ができ、リリースノートに直した PR が載っていればOK。

### 演習4（早く終わった人向け）：他の人のリポジトリに貢献する

他の人の発表で「こうしたらいいのに」と思ったことを、その人のリポジトリに **Issue** として丁寧に書く。相手が了解すれば、フォークして PR を送ってみる。

**確認方法**：他の人のリポジトリに、自分が書いた Issue か PR が1つ以上あればOK。

> 他の人のリポジトリに PR を送るのは、オープンソースへの貢献と同じ流れ。フォークから来た PR では Secrets が使えないこと（コマ19）も、ここで実感できる。

##  まとめ

### この授業でできるようになったこと

- Next.js で画面を作り、**テストで守り**、**GitHub Actions で自動でチェックし**、**自動で公開する** 流れを、自分の手で一通り作れるようになった
- うまくいかないときに、ログやテストの結果から原因を探して直せるようになった
- 作ったものと作り方を、他の人に説明できるようになった

### 最後に

30コマで作った CI/CD のパイプラインは、これから作るどんなアプリにもそのまま使える。**「作る → 守る → 自動化する → 届ける → 説明する」** を、次のアプリでもくり返していこう。
